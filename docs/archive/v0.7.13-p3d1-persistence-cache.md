## 关键证据

### 1. PERSISTENCE LOAD CACHE 工作正常（非根因）

纯 persistence 实验（文档第五节）：
```
save(V1) → load: V1 ✓
save(V2) → load: V2（blocks=1, refs=195）✓
new instance load: V2 ✓
load == disk ✓
```
内存 mock（mtime 精确递增）下 load cache 完全正确。

### 2. save 后 cache 不更新（潜在风险，但 mtime 兜底）

persistence.ts L293-304：save() 写盘后**不 cache.set / cache.delete**。
但 load() L206 用 `cached.mtime === mtime` 判断——**只要 mtime 变化，cache 自动失效**。
仅在 mtime 碰撞（同 ms 连续写）时才可能命中旧 cache（本实验未复现）。

### 3. GLOBAL CACHE SHARING = YES（文档第七节）

persistence.ts L170-176：cache 挂在 `globalThis.__acpLoadCacheV2`，
跨 createPersistence 实例共享（runtime-wide）。

### 4. SAVE GUARD SOURCE = cache + disk 混合（文档第九节）

persistence.ts L240：`cache.get(path)?.mtime === info.mtimeMs ? cache.get(path)?.state : ...`
→ currentVersion 优先来自 cache，cache miss 时读 disk。
**若 cache 过期（旧 V1 且 mtime 巧合相等），guard 可能被绕过**——理论风险，
本次取证未复现（mtime 精确）。

### 5. 根因 = 旧 runtime stale-write（P3-D 部署前）

tool_params.log 时间线：

→ 磁盘最终 blocks=0, compressFailed=1（覆盖后 compress 计数被旧 state 覆盖丢失）
