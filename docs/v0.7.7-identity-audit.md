## 1. Executive Summary

通过**宿主真实源码（AAswordman/Operit）+ 插件真实算法（stableKeyForTurn）+ 实机 state/raw 数据**三方取证，得出：

- Operit 的 PromptTurn **不携带任何宿主稳定 ID**（无 messageId / toolCallId / timestamp）
- ACP 的 CoreMessage.id **完全基于 content hash**（`kind|toolName|hash`）
- 实机 coverage：USER 79.4% / ASSISTANT 70.3% / TOOL_CALL 68.1% / TOOL_RESULT 64.5% / SYSTEM 10.0%
- **identity 部分稳定，非全断**。断点主要是：易变工具结果、每轮重拼的 SYSTEM、SUMMARY 占位重算

## 2. Operit Identity Source

**问题 1：Operit 的稳定 host identity 是什么？**

| 层级 | 稳定 ID | 来源 | 传递到 PromptTurn？ |
|---|---|---|---|
| DB message | `message.id`（ChatMessage） | ChatHistoryManager/DB | ❌ 无 |
| PromptTurn | **无 id 字段** | PromptTurn.kt:26-31 | — |
| ChatMessage.toolCallId | 有（host 内部） | ChatMessage | ❌ 未写入 PromptTurn.metadata |

**源码定位**：`PromptTurn.kt:26-31`：
```kotlin
data class PromptTurn(
    val kind: PromptTurnKind,
    val content: String,
    val toolName: String? = null,
    val metadata: Map<String, Any?> = emptyMap()
)
```
**没有任何 id/timestamp 字段**。metadata 是唯一可能携带 identity 的地方，但实测宿主在 `processChatMessageWithTools`（ConversationService.kt:726-826）**从不写入 metadata**（恒 emptyMap）。

## 3. PromptTurn Identity Analysis

**问题 2：PromptTurn 是否保留 host identity？**
- ❌ **不保留**。PromptTurn 只有 kind/content/toolName/metadata。
- 跨 Hop 唯一可能稳定的是 **content 本身**（若宿主不重排/不改写）。

## 4. ToolCall / ToolResult Identity Analysis

**问题 3：TOOL_CALL / TOOL_RESULT 是否有稳定 identity？**

| 项 | 情况 |
|---|---|
| toolCallId（host） | ChatMessage 内部有，但 **processChatMessageWithTools 不写入 PromptTurn**（ConversationService.kt:767-776 只放 content） |
| toolName | 有，但 toolName 不作为跨 Hop 稳定 id |
| XML 内嵌 id | TOOL_CALL content 里可能有 `<tool_call_id>` 但非强制 |

**问题 4：拆分后能否追溯回同一 host message？**
- ❌ **不能**。`processChatMessageWithTools` 把一条含工具 XML 的 message 拆成多个 PromptTurn（ASSISTANT/TOOL_CALL/TOOL_RESULT），**拆分后的各 turn 不共享任何 parent id**（ConversationService.kt:726-826，全用 `PromptTurn(kind, content)`，无关联字段）。

## 5. CoreMessage.id Generation

**问题 5：CoreMessage.id 当前如何生成？**

**精确代码**：`src/acp/messages.ts:86-101` + `:115-136`：
```ts
export function stableKeyForTurn(turn): string {
  const kind = turn.kind || "UNKNOWN";
  const content = typeof turn.content === "string" ? turn.content : "";
  const toolName = turn.toolName || "";
  // 排除 toolCallId 等易变 metadata
  ...
  return `${kind}|${toolName}|${hashString(JSON.stringify([content, meta]))}`;
}
// promptTurnsToCoreMessages:
const core = { id: stableKeyForTurn(turn), role, contentType, text };
```

**结论**：CoreMessage.id = **content hash（+ kind + toolName + 稳定 metadata）**。**不含** host message id、不含 index（仅重复 content 时加 `#2` 后缀）、不含 UUID。

## 7. Coverage / Intersection Table

**问题 7：第一次断裂发生在哪一个转换阶段？**

```
按 kind 的 identity 覆盖率（byRaw 累积 vs 当前 raw turns）:
  TOOL_RESULT  64.5%   ← 最易断
  TOOL_CALL    68.1%
  ASSISTANT    70.3%
  USER         79.4%   ← 最稳定
  SYSTEM       10.0%   ← 几乎全断
  SUMMARY      50.0%
```

**断点阶段判定**（结合宿主源码）：
- **SYSTEM 10%**：宿主每轮 `SystemPromptConfig.getSystemPromptWithCustomPrompts` 重新拼接（含 workspace/roleCard/memory）→ content 几乎每轮变
- **TOOL_RESULT 64.5%**：`normalizeToolResultMarkupForModel`（ConversationService.kt:689-713）+ 工具输出含动态时间戳/路径/随机内容
- **SUMMARY 50%**：压缩块占位 content 每轮可能重算（被 ACP 自身替换）

**这不是 kernel bug**——是 adapter 的 id 策略（纯 content hash）对"每轮 content 变化"敏感的自然结果。

## 8. Exact Breakpoint

| 阶段 | 是否断 | 原因 |
|---|---|---|
| DB message → PromptTurn | ❌ 无 id 可断 | 宿主不传递 id |
| PromptTurn → CoreMessage | ⚠️ 依赖 content | stableKey = content hash |
| CoreMessage → kernel ref | ✅ 稳定 | assignRefs 按 id 复用（id 不变则 ref 不变） |
| compress block covered | ✅ 稳定 | block 存 ref/covered ids |
| block → next Hop projection | ⚠️ 部分 | 新 turns 若 content 变则新 id → covered 不命中 |

**结论**：identity 断裂的本质 = **adapter 用 content hash 当 id**，而宿主对部分内容（SYSTEM/工具结果）每轮会改写 → hash 变 → 新 id → 旧 block 覆盖不命中 → 压缩"看起来没生效"。

## 9. Adapter-level Fix Proposal（不修改 kernel）

按文档推荐结构设计 **ACP Identity Bridge**：

```
Operit PromptTurn[]                    ← host 无 id
        ↓
ACP Identity Bridge（新增 identity-bridge.ts）
  ├─ 第一优先级：稳定 id（若未来宿主传入 metadata.id/toolCallId）
  ├─ content hash fallback（现状）
  └─ 附加稳定化：toolCallId 用 XML 内嵌 id 而非 FIFO；SYSTEM 排除动态段
        ↓
stable CoreMessage.id
        ↓
acp-kernel（无需改）
```

关键改进点（**都改 adapter 层，不动 kernel**）：
1. **TOOL_CALL/TOOL_RESULT**：优先用 XML 内嵌 `<tool_call_id>`/`invocationId`（当前 messages.ts:162-175 已尝试 tagId，但 FIFO 配对会漂移）→ 改用稳定 call id 作为 id 组成部分
2. **SYSTEM**：SYSTEM 每轮变是因为宿主重拼 → 考虑 id 忽略 SYSTEM 或只 hash 稳定前缀
3. **compress 命中增强**：covered 判定从"精确 id 匹配"放宽到"id 或 content 相似匹配"（可选，后续）

## 10. Why acp-kernel Does / Does Not Need Changes

**NOT_YET_PROVEN（倾向 NO）**：
- kernel 的 assignRefs 按 message.id 复用映射（`if (map.byRaw[message.id]) continue`）——**id 不变则 ref/block 稳定**
- identity 断裂的根源在 adapter 的 id 生成策略（content hash），**不在 kernel**
- 若 adapter 提供稳定 id，kernel 无需任何修改
