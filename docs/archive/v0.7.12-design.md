## 1. CURRENT REGRESSION MODEL

V0.7.6 删除 preflight 后：

```
hard (effective >= 170K)
  → forced nudge（仅提示）
  → raw history（4045条/829万字符/ACP estimate 255万）
    直接进入 Operit finalize
  → applyPromptFinalizeHooks 采用 ACP mutation（V0.7.6 无折叠 → preparedHistory ≈ raw+1）
  → estimatePreparedRequestWindow(calculateInputTokens(requestHistory)) = 80万
  → provider actual = 90.5万
```

关键机制确认（V0.7.11 证据）：
- Operit finalize **确实采用** hook 返回的 preparedHistory 作为 requestHistory（EnhancedAIService 1062-1117）
- 所以 ACP 若返回折叠后的 preparedHistory，**真实 request 也会被压**（不是 fake）
- V0.7.5 正是因此把 estimator 输入压到 ~15万

## 2. DESIGN OPTIONS

### 方案 A：恢复 V0.7.5 Preflight
- 触发：hard
- 谁决定：ACP 自动
- 层次：projection + state mutation
- 修改 requestHistory：是
- 影响 actual：是（真实变小）
- billion-context 语义：冲突（ACP 替模型决定压什么）
- stale/mismatch：无（真压缩）
- Tool Loop：好
- 风险：模型失去压缩决策权

### 方案 B：Hard Forced Nudge Only（现状）
- 触发：hard
- 谁决定：模型
- 层次：仅提示
- 修改 requestHistory：否
- 影响 actual：否（当前 request 仍 800K）
- billion-context 语义：保留
- stale/mismatch：**有**（request 800K 进 estimator）
- Tool Loop：好
- 风险：当前 request 超 hard 无法保护

### 方案 C：Temporary Protected Projection（重点）
- 触发：hard
- 谁决定：ACP 构造，但**不永久 mutation CompressionState**
- 层次：仅 projection 输出
- 修改 requestHistory：是（返回折叠后的 preparedHistory）
- 影响 actual：是（真实变小）
- billion-context 语义：保留（非永久 block，模型仍可自己 compress）
- stale/mismatch：需保证 stage1≈stage2≈final
- Tool Loop：需验证
- 风险：identity/continuity

### 方案 D：模型驱动 Compress Round-trip
- 触发：hard
- 谁决定：模型
- 层次：暂停 request → 模型 compress → 重建 request
- 修改 requestHistory：是
- 影响 actual：是
- billion-context 语义：最贴近原版
- stale/mismatch：无
- Tool Loop：复杂
- 风险：延迟/成本/流式/失败恢复（文档明示过高可记录不做）

## 4. RECOMMENDED ARCHITECTURE

**推荐：方案 C（Temporary Protected Projection）+ 方案 B 的 forced nudge 并行**

设计原则（文档第四节状态机）：
- **两个职责显式分离**：
  - `FORCED_PRESSURE`：强制告诉模型必须压缩（nudge 语义）
  - `SEND_CONTEXT_PROTECTION`：hard 时不让超限 context 原样进 estimator（projection 语义）
- hardLimitPct 不再兼任两职；新增 `protectedTarget` 概念

关键实现策略（避免 fake accounting）：
- protected projection **必须是真正返回给 host 的 preparedHistory**（不是只在 estimate 里做）
- 这样 estimator input == actual requestHistory（文档十三节要求）
- 不永久 mutation CompressionState：protected view 是**发送视图**，decompress 仍可恢复原文

## 5. DATA FLOW

```
RAW (4045条 / ACP estimate 255万)
  → PRESSURE (effective >= hard 170K → FORCED)
  → FORCED_PRESSURE (forced nudge 注入，模型看到)
  → SEND_CONTEXT_PROTECTION (构造 protected send-view)
       ├─ 复用已形成 block 的 SUMMARY（已有 45 block 的真实摘要）
       └─ 对未覆盖的巨型 TOOL_RESULT 做 absorb 候选标记（不自动 absorb）
  → FINALIZE (before_finalize_prompt: 返回 protected preparedHistory)
  → FINALIZE (before_send_to_model: 返回同一 protected view，不重建)
  → ESTIMATE (calculateInputTokens(protected requestHistory) ≈ 保护目标)
  → REQUEST (provider 收到 protected requestHistory)
```

## 6. STATE OWNERSHIP

| State | 拥有者 | 修改者 | V0.7.12 变化 |
|---|---|---|---|
| CompressionState | ACP kernel | 仅模型 compress / absorb | 不变（protected view 不 mutation 它）|
| Projection（send view）| ACP adapter | ACP projection | **新增：hard 时返回 protected view** |
| IdentityState | ACP identity-bridge | ACP | 不变 |
| UsageState | ACP usage-manager | ACP | 不变 |
| Operit estimate | Operit AIService | Operit calculateInputTokens | 不变（但输入变 protected）|

## 7. TEST PLAN（文档九节 8 个测试）

1. raw=800K hard=170K → final request <= protection target
2. hard not reached → no automatic compression
3. hard reached → forced nudge exists
4. hard + model compresses → next hop uses compressed state
5. hard + model does not compress → send protection active
6. Tool Loop hop → protected projection survives
7. Stage1 → Stage2 → projection doesn't expand
8. compression + protected projection → identity/compression continuity

## 8. RISK REGISTER

- **Tool Loop**：内部 hop 不走 finalize，需在 processToolResults 后也复用 protected view
- **double finalize**：stage1/stage2 必须返回同一 protected view（防 stage2 恢复 raw）
- **identity continuity**：protected view 不能破坏 byRef/bridge 映射
- **cache contamination**：protected view 不应写入 projectionCache（污染后模型 compress 用旧缓存）
- **provider mismatch**：estimate 与 actual 天然有 gap（80万 vs 90.5万），目标是"同一视图"，不要求数值相等
- **stale currentWindowSize**：Operit DB 仍存 stale estimate，需宿主侧配合或接受（非 ACP 可改）

## 最终结论（文档十四节）

- Q1 是否恢复 preflight？**不恢复**（语义冲突）
- Q2 不恢复谁保护当前 request？**Send Context Protection（protected projection）**
- Q3 forced nudge 足够吗？**不足**（当前 request 仍 800K）
- Q4 protected projection 能否稳定？**设计上可行**（host 采用 hook 返回的 preparedHistory），需 V0.7.13 验证两阶段
- Q5 必须改 Kernel？**否**（kernel 已支持 block 复用/absorb）
- Q6 必须改 Operit host？**不需要**（hook 机制已允许替换 preparedHistory）
- Q7 必须改 identity bridge？**需谨慎**（protected view 与 bridge 共存，V0.7.15 验证）
- Q8 如何保证 protected 150K 不会 actual 800K？**protected view = 实际返回的 requestHistory**（不是 estimate-only）→ estimator 与 provider 收到同一份
