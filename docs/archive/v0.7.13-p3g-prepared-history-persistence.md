# V0.7.13-P3-G：preparedHistory 是否进入宿主后续上下文的宿主源码审计

日期：2026-09-09
状态：取证完成（未改任何代码）

---

## 结论速览

```
preparedHistory 只进入本次请求，没有进入后续历史（结论 2）
```

## 完整证据链（文档 E 要求）

```
用户历史
  → DB 原始消息（ChatHistoryManager.persistMessageLocked L665-687）
  → 宿主读 DB → chatHistory（原始）
  → ACP project() → preparedHistory（投影/压缩后）
  → 本次请求发送 preparedHistory（压缩生效）
  → 宿主把【原始消息】写回 DB（persistMessageLocked：messageDao.insertMessage 原始内容）
  → 下一轮又从 DB 读【原始历史】
  → ACP 再次投影
  → 上下文再次膨胀
```

## 断点

**preparedHistory 与宿主 DB 历史是两套数据**：
- preparedHistory：ACP 每次 finalize 临时生成，只用于本次发送
- DB 历史：宿主持久化原始消息（ChatMessage 原文），**不感知 ACP 投影**

## 宿主源码位置

| 位置 | 内容 |
|---|---|
| EnhancedAIService.kt L700-715 | estimatePreparedRequestWindow：calculateInputTokens(preparedHistory) → UI 计数用投影 ✅ |
| EnhancedAIService.kt L769+ | estimateRequestWindowFromMemory：finalize 钩子 → 投影 preparedHistory |
| ChatHistoryManager.kt L665-687 | persistMessageLocked：原始 ChatMessage 写 DB（不感知投影） |
| AIMessageManager.kt L700-710 | 消息持久化走 addMessage → persistMessageLocked（原始） |

## 影响

1. **UI 计数下降** ✅（算的是投影 preparedHistory）
2. **DB 历史不变** ⚠️（原始消息保留，压缩成果不持久）
3. **下一轮重新膨胀** ⚠️（从 DB 读原始历史 → ACP 重新投影，开销重复）
4. **不压缩也会跌**：插件 capProjectionSize（totalBudgetChars=200_000）对超预算投影截断旧消息
   （keepChars 2000→500），与 ACP compression 无关——这是"非压缩性下跌"的真正机制。
   （P3-G 初版误判为宿主图片/媒体裁剪，用户确认从未发送图片/媒体，已修正。）

## 修复方向（待确认，本轮不改）

- 需要宿主侧把 ACP 投影**持久化**（写回 DB 替换原始消息），或
- 宿主支持"压缩消息"写入（summary 消息替换历史区间），或
- ACP 在宿主 DB 中写入 block 摘要消息并标记原消息为压缩

**关键约束**：改宿主 DB 是高风险操作，必须先确认宿主是否有"消息替换/压缩写入"的合法接口。
